# Firebase — connection, auth and Firestore

Written **2026-08-06**. Covers how this app connects to Firebase, what is already configured, what
still isn't, and the exact console steps for the gaps.

> **No secret values appear in this document.** Credentials are referenced by their `.env` key name
> only. `.env` is gitignored (`.gitignore` lines 2–3) and must never be committed — the same rule the
> DeepSeek key follows, and the whole reason the runtime `.env` loader exists.

Platform app ids are mapped in `firebase.json`. Note **Windows reuses the web app id**
(`…:web:7fbe03598033c50f25d30a`) — that's the standard FlutterFire desktop arrangement, not a mistake.

## What's wired today

`Firebase.initializeApp()` runs **before the first frame**, in `lib/main.dart`:

```dart
try {
  await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);
} catch (_) {
  // Optional at boot; the dashboard runs fine without Firebase.
}
```

**Fail-soft on purpose** — mirroring the repository's fallback ethos. A Firebase hiccup must never
block the dashboard, which is entirely public market data and needs no account.

`firebase_core` is the **only** Firebase package currently in `pubspec.yaml`. It registers on Windows
(see `windows/flutter/generated_plugin_registrant.cc`).

## Firestore

### Rules — as they stand
`firestore.rules` already requires an authenticated user:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if request.auth != null;
    }
  }
}
```

> ⚠️ **Nothing in the app signs in yet.** Until auth exists, every Firestore read and write returns
> `PERMISSION_DENIED`. This is the blocker for persistence, not a bug in the rules.

### Rules — target
Once sign-in exists, tighten to per-user isolation:

```
match /ephedrine2010/{uid} {
  allow read, write: if request.auth != null && request.auth.uid == uid;
}
```

Deploy with:
```bash
firebase deploy --only firestore:rules
```

### Planned data shape
All user data lives under one root collection, **`ephedrine2010`**, one document per signed-in user:

```
ephedrine2010/{uid}
  {
    my_stocks: {
      us: [ {marketId, symbol, name, query, provider}, … ],
      sa: [ … ],
      cr: [ … ]
    },
    updatedAt: <server timestamp>
  }
```

A single document means **one read at boot** and one write per change — the cheapest and most atomic
option — with room for `settings`, `alerts` and so on as sibling fields or documents later.

**Only identity is ever stored — never a price, change or dividend.** Those re-fetch live every time.
A stored number would be read as a current one; this is the same rule the price curves follow when
they return "N.A." rather than a mocked line.

## Authentication

**Decision: real Google sign-in**, and **only the "My stocks" section is gated**. The dashboard,
tiles, screener, market details and price charts all work signed-out exactly as they do today — that
data is public and needs no account, and an auth outage must not produce a blank app.

### Console setup — state

| # | Item | Where | State |
|---|---|---|---|
| 1 | Google provider enabled | Firebase → Authentication → Sign-in method | ✅ **Done** |
| 2 | OAuth 2.0 **Desktop** client (for Windows) | Google Cloud → APIs & Services → Credentials | ✅ **Done** — values in `.env` |
| 3 | Android SHA-1 fingerprint | Firebase → Project settings → Your apps → Android | ❌ **Not landed** |
| 4 | Web authorized JavaScript origins | Google Cloud → Credentials → *Web client* | ❌ Not done (web only) |

### 2 — the desktop OAuth client

Read at runtime from `.env` by these key names:

```
GOOGLE_OAUTH_CLIENT_ID
GOOGLE_OAUTH_CLIENT_SECRET
```

Both are present on the original development machine. **`.env` is gitignored**, so a fresh clone will
not have it — recreate the file from the old machine or re-issue the credentials.

No redirect URI needs registering: Google permits installed-app clients **any loopback port**, so the
flow claims `http://127.0.0.1:<free port>` at runtime.

> A desktop client's "secret" is **not confidential** — it ships inside the binary. What actually
> secures this flow is **PKCE**. That's expected for the OAuth installed-app flow; it is not a reason
> to hardcode the values, which must stay in `.env`.

### 3 — the Android SHA-1 (currently failing)

`android/app/google-services.json` still reads `"oauth_client": []` after two re-downloads. When a
fingerprint is registered **and** Google Sign-In is enabled, that array gains a `client_type: 1` entry
carrying `android_info.certificate_hash`. An empty array means the fingerprint is not saved on the
Firebase **Android app**.

Debug keystore SHA-1:
```
99:41:10:95:5F:9B:A3:F0:3F:08:83:C1:A3:F0:16:5C:17:0B:FA:F1
```

Re-read it any time (Git Bash):
```bash
keytool -list -v -alias androiddebugkey \
  -keystore "$USERPROFILE/.android/debug.keystore" \
  -storepass android -keypass android
```

Steps:
1. Firebase console → ⚙️ **Project settings** → **Your apps** → the **Android** app
   (`com.example.stocks_etfs_eye`) — *not* the web app.
2. **Add fingerprint** → paste the **SHA1** line above (not SHA256) → **Save**.
3. Re-download `google-services.json` → replace `android/app/google-services.json`.
4. Verify it took: the file should now contain a non-empty `oauth_client` array.

This covers the **debug** keystore only — `flutter run` and debug APKs. A release build needs that
keystore's SHA-1 added the same way, or Google Sign-In fails only in release.

**Android-only. Blocks nothing on Windows or web.**

Unrelated but worth noting: the package is still `com.example.stocks_etfs_eye`. Fine for development;
the Play Store will not accept a `com.example.*` package.

### 4 — web authorized origins

Web build only; skip it while working on Windows.

**a.** Firebase console → **Authentication** → **Settings** → **Authorized domains** — confirm
`localhost` is listed (usually is by default); add the production domain when deploying.

**b.** Google Cloud console → **APIs & Services** → **Credentials** → open **"Web client (auto created
by Google Service)"** (*not* the Desktop client):
- **Authorized JavaScript origins** → add `http://localhost:5000`
- **Authorized redirect URIs** → add `https://stocketfseye.firebaseapp.com/__/auth/handler`

The port matters: Flutter's web dev server picks a **random** port each run, which would break the
origin every time. Pin it:

```bash
flutter run -d chrome --web-port=5000
```

## Windows sign-in — the loopback OAuth flow

Because `google_sign_in` doesn't support Windows:

1. Start a local `HttpServer` on `127.0.0.1:<free port>`.
2. Launch the system browser to Google's auth endpoint with **PKCE** (`code_challenge`), the client id
   from `.env`, and `redirect_uri=http://127.0.0.1:<port>`.
3. Catch the redirect, exchange `code` + `code_verifier` for tokens.
4. `GoogleAuthProvider.credential(idToken: …)` → `FirebaseAuth.instance.signInWithCredential(…)`.

Needs `url_launcher` (not yet a dependency). Build this **last** — it's the riskiest piece, and
mobile/web sign-in works with the package alone.

## Rules to keep

- **Never embed a secret in the client.** Keys come from `.env` at runtime (native) or live behind
  the proxy (web).
- **Fail soft.** Firebase being unreachable must never blank the dashboard.
- **Store identity, not values.** No prices in Firestore.
- **Don't gate public data.** Sign-in guards the user's own list, nothing else.
